# Bible Reader for Chromebook — Plan

Written 2026-10-09, revised the same day after two rounds of review. A
listening-first Bible app for people with low vision, specifically macular
degeneration (loss of central vision). Chromebook first. iOS may follow
later; section 10 lists what that changes today.

A clickable mockup of the current layout lives at
`mockups/reader-layout-v3.html`, published at
https://claude.ai/artifact/EdpCRep1ecmTW59VhEp8iu (private; opens for the owner). Decisions
and open items are logged in section 11.

---

## 1. Who this is for, and what that changes

Macular degeneration takes away the center of the visual field. People see
around the edges, often with magnification, and glare and low contrast make
things vanish. Fine pointer control is hard. The app therefore follows these
rules everywhere:

- **Huge targets.** Every control is a button, usually a full row tall, with
  generous gaps so a near-miss hits nothing instead of the wrong thing.
- **One idea per row.** Each row of the reader does one thing: testament,
  book, chapter, play and verses, settings. Previous is always on the left,
  Next on the right. Nothing moves between sessions.
- **High contrast, thick edges.** Two dark schemes and two light schemes.
  Every button has a thick border so its edge is visible even when the fill
  is not. Contrast is 19:1 or better.
- **Audio for everything.** Every action speaks a short confirmation. Every
  jump announces where you landed. Any control can be read aloud without
  activating it.
- **Forgiving input.** Buttons can be set to activate on click or only
  after being held, with an adjustable hold time. Accidental
  double-activations within 400 ms are ignored. A pressed button flashes.
  Keyboard shortcuts cover the main controls.
- **Remembers everything.** Position and settings persist. Reopening the app
  lands exactly where the person stopped.

## 2. Platform decision

**Build an installable web app (PWA), hosted on GitHub Pages, installed on
the Chromebook from Chrome.**

Why this and not something else:

- Chrome Apps (the old packaged format) are discontinued. The modern way to
  put an app on a Chromebook without the Play Store is a PWA. It installs to
  the shelf, opens in its own window without browser chrome, and works
  offline.
- GitHub Pages is free, HTTPS, and you already have GitHub. Deploy is a push.
- The same code becomes an iOS app later by wrapping it with Capacitor. iOS
  costs a wrapper, not a rewrite.
- Chrome on ChromeOS has built-in text-to-speech voices available to web
  pages through the Web Speech API. If those prove unsatisfactory, the same
  player can play pre-generated audio instead (section 4.3).

**Stack**

| Piece | Choice | Reason |
|---|---|---|
| Build tool | Vite + TypeScript | Small, fast, standard, Capacitor-friendly |
| UI framework | None (plain DOM + small modules) | Four screens, little state. Zero runtime dependencies, easy to audit for accessibility. The mockup is already written this way |
| Offline/install | vite-plugin-pwa (Workbox) | Precaches the app and all Bible text, auto-updates silently |
| Speech | Web Speech API behind a `VerseReader` interface | Device voices work with no infrastructure; the interface lets pre-generated audio replace them later |
| Storage | localStorage behind a small `storage` module | Simple; iOS can swap in Capacitor Preferences later |
| Font | Atkinson Hyperlegible (bundled) | Designed by the Braille Institute for low vision; free |
| Hosting | GitHub Pages | Free at this size |

Dev machine (this Mac): Node 26, npm, gh (signed in), git, Python 3 and
Xcode are installed. The app's in-app preview launcher cannot read the
Desktop folder, so local previews serve a copy of `dist/` from the session
scratchpad (see the uncommitted `.claude/launch.json`).

## 3. Bible text

**Translation: King James Version (KJV).** Decided. Public domain in the
US, and the translation most older listeners already know by ear.

- The data pipeline is translation-agnostic. The World English Bible (WEB,
  modern English, public domain) could be added later by running the build
  script again.
- NIV, ESV, NLT and similar require a license, usually an online API, and
  separate audio rights. Not in scope.
- Source data: `scrollmapper/bible_databases` on GitHub, `formats/json/KJV.json`
  (verified: 31,102 verses, 790,892 words, 4.11 million characters,
  average 25 words per verse, longest verse 90 words). Its book names use
  Roman numerals ("I Samuel") and "Revelation of John"; the build script
  normalizes them to "1 Samuel" and "Revelation". Spot-check a few chapters
  against a printed KJV.

**On-disk format the app uses** (generated by `scripts/build-bible.ts`):

```
public/bible/kjv/books.json      -> [{ id:"GEN", name:"Genesis", short:"Gen.", spoken:"Genesis", testament:"OT", chapters:50 }, ...]
public/bible/kjv/GEN.json        -> { id:"GEN", name:"Genesis", chapters:[ ["In the beginning...", "And the earth..."], [...] ] }
```

- One file per book so a book loads in well under a second. Psalms, the
  largest, is about 260 KB. The whole KJV is about 4.5 MB uncompressed and
  is precached for offline use.
- `short` is the abbreviation shown when the full name would wrap
  ("1 Thess.", "Song of Sol.", "Eccles."). `spoken` is a pronunciation
  override for the voice: "Job" must be spoken "Jobe", not like the
  occupation. Others: Philemon, Habakkuk, Haggai.
- Text cleanup in the build script: strip pilcrows, bracketed italics
  markers, Strong's numbers. For speech only, convert all-caps "LORD" and
  "GOD" to "Lord" and "God" so no voice spells them letter by letter.
- A small `pronounce.ts` substitution map handles in-text names the voice
  mangles. Start empty and add words as they are noticed.

## 4. Speech

### 4.1 How reading works (independent of which voice is used)

**One verse at a time.** The player reads verse N, highlights it, and when
it ends moves to verse N+1. At the end of a chapter it announces the next
chapter and keeps going (setting: "Keep reading into the next chapter",
default on). Exact verse-level highlighting falls out of this design.

**Pause means stop and remember.** Decided. Pause stops the voice and keeps
the current verse; Play reads that verse again from its beginning.

**Announcements** (short, always before content):

- Jump to a chapter or book: "John, chapter 4."
- Manual verse jump: "Verse 17." then the verse.
- Button press: a two-word confirmation, "Next chapter." (setting: "Speak
  button names", default on).
- Verse numbers during continuous reading: never spoken. Decided.

**Behavior when paused versus playing**

| Action | While playing | While paused |
|---|---|---|
| Next/Prev Verse | Jumps, announces verse number, keeps reading | Reads that one verse, then stops |
| Next/Prev Chapter or Book, Testament button | Announces the new place, reads from verse 1 | Announces the new place only |
| Choose Book/Chapter | Announces the new place, reads from verse 1 | Announces the new place only |
| Read a control's name | Pauses, reads the name, resumes the current verse | Reads the name |

### 4.2 Voice: the Chromebook's own voices first (decided)

The Web Speech API (`speechSynthesis`) uses whatever voices ChromeOS has.

- ChromeOS ships two engines. "Chrome OS TTS" is the better one; "eSpeak"
  is the robotic one and should be avoided. Higher-quality voice packs for
  Chrome OS TTS are downloadable: Settings › Accessibility › Text-to-speech
  › Text-to-speech voice settings › next to "Chrome OS built-in
  text-to-speech extension" choose Settings › Install next to English.
  Do this once on the target Chromebook before judging the voices.
- Expectation: noticeably better than the stock voice, still recognizably
  synthetic. The "natural voice when online" option in ChromeOS
  Select-to-speak is a ChromeOS feature and is not expected to be reachable
  from a web app; milestone M0 checks exactly which voices the app can see.
- The mockup already speaks through the device voice, so it doubles as a
  first listening test on the Chromebook.
- Testing on the Mac: Chrome lists the macOS system voices. The stock ones
  (Samantha, Daniel, Karen) are ordinary. Better ones are downloaded under
  System Settings › Accessibility › Spoken Content › System voice › Manage
  Voices, choosing an Enhanced or Premium English voice such as Ava, Zoe,
  Evan or Tom, then relaunching Chrome. The mockup hides the macOS novelty
  voices (Bubbles, Zarvox and friends) from its voice list.
- Known Chrome quirks and how the design handles them:
  - Voices load asynchronously (`voiceschanged`). Wait for them; fall back
    to the default voice.
  - Google "network" voices cut off utterances longer than about 15
    seconds. Nearly half of KJV verses exceed 25 words, so verses are split
    at clause boundaries into several utterances while the highlight stays
    on the one verse. Prefer local voices in the voice list.
  - Chrome may refuse to speak before the user has interacted with the
    page. The app never auto-plays on launch.
  - Always `cancel()` before `speak()`.

### 4.3 Fallback if the voices disappoint: pre-generated natural audio

Kept in reserve, to revisit after the initial build. Generate the entire
KJV once with a modern neural voice, store one audio file per chapter plus
a JSON index of where each verse starts, and play it with an ordinary
`<audio>` element. The app never calls a speech service at runtime.

| Step | Detail |
|---|---|
| Engine choices | Google Cloud Chirp 3 HD ($30 per million characters, 1 million free each month), Google Neural2 ($16 per million, 1 million free each month), or free open-source models run on this Mac: Kokoro (Apache 2.0) or Chatterbox (MIT). |
| One-time cost | About $93 with Chirp 3 HD in one month, about $50 with Neural2, $0 spread over five months of free tier, or $0 with Kokoro or Chatterbox. |
| Size and hosting | About 85 hours, 1.2 to 1.8 GB. Cloudflare R2 hosts that free (10 GB, free egress). Chapters cache on demand; a "Download all audio" button stores everything. |
| Benefits | Human-like voice, reliable pause and resume, speed by `playbackRate`, simpler background audio on iOS. |

Human-read options (LibriVox public-domain KJV; Faith Comes By Hearing's
Bible Brain API with verse timings, approval-gated and free for ministry
apps) are licensing questions and not planned.

### 4.4 The interface that keeps both options open

```ts
interface VerseReader {
  load(bookId: string, chapter: number): Promise<void>;
  play(verse: number): void;          // starts at that verse; fires onVerseStart / onChapterEnd
  stop(): void;
  setRate(rate: number): void;
  onVerseStart: (verse: number) => void;
  onChapterEnd: () => void;
}
```

`TtsReader` speaks verse text through the device voice. `AudioReader`
(later, if needed) plays a chapter file and raises verse events from the
timing index. The rest of the app is identical.

Rules and behaviors:

- **Abbreviate instead of wrapping.** A name is shown in full if it fits
  on one line, otherwise as its abbreviation ("1 THESS.", "SONG OF SOL.",
  "CHAP. 3"). Only if even that does not fit does it wrap. The spoken name
  is always the full name.
- **Testament button**: shows the current testament and switches to the
  other one. Pressing NEW TESTAMENT goes to Genesis 1, verse 1, and the
  button then reads OLD TESTAMENT. A small caption under the name says
  "press for Old Testament". Announces "Old Testament. Genesis, chapter 1."
- **Book arrows**: previous or next book at chapter 1, verse 1. Crossing
  from Malachi to Matthew changes the testament button. **Book name**:
  opens the book list for the current testament.
- **Chapter arrows**: previous or next chapter at verse 1, crossing book
  boundaries. **Chapter name**: opens the chapter list for the current
  book.
- **Verse arrows**: previous or next verse, crossing chapter boundaries.
  **Play/Pause**: filled button, label and glyph change with state.
- **Settings**: full-width row at the very bottom, shorter than the others.
- **Arrows-only view** (setting): the book and chapter name buttons are
  hidden and the arrows widen to half a row each. Book arrows carry an
  open-book icon and double chevrons; chapter arrows a page icon and a
  single chevron. The lists stay reachable from the keyboard (B and C).
- **Scripture panel**: shows the current chapter and keeps the line being
  read at the vertical center, gliding continuously as the voice moves
  through a verse and on to the next one (word positions from the voice
  when it reports them, timing otherwise). No ring or highlight marks the
  verse; its position is the marker. Reading a control's name on the panel
  speaks the current reference.
- Rows that are adjacent and similar (book arrows above chapter arrows) are
  separated by the row gap and distinguished by the small caption under
  each arrow glyph ("BOOK", "CHAP.", "VERSE").

### 5.2 After choosing a book (decided: start at chapter 1)

Choosing a book in the book list returns to the reader at chapter 1,
verse 1, announced "John, chapter 1." The chapter arrows or the chapter
name take it from there. Each picker does one job and comes home.

Opening a picker pauses the reading. Choosing a place restarts it there if
it was playing. BACK with nothing chosen returns exactly to where you were.

## 6. Cross-cutting accessibility behaviors

**Two activation modes (setting)**

| | Click mode (default) | Hold mode |
|---|---|---|
| Activate a button | Click or tap | Hold for the set time. A progress fill crosses the button while holding; releasing early does nothing |
| Hear a button's name without activating | Right-click, or press and hold about 0.9 s | Any press shorter than the hold time, or right-click |
| Keyboard Enter or Space | Activates | Activates (keyboard presses are deliberate) |

Hold mode exists for people whose hands brush or tremble on the trackpad.
Nothing happens unless a button is held on purpose, and a stray tap simply
reads the name of what was touched.

Spoken names are statuses, never instructions. The CLICK button says
"Click mode, selected" and the HOLD button says "Hold mode". In hold mode a
press that ends early reads the name and adds "Hold to activate", so a tap
that did nothing explains itself.

**Right-click on mouse and trackpad**

- Handle `contextmenu`, suppress the native menu, speak the control's
  accessible name. This covers the right button of a mouse, a two-finger
  click or two-finger tap on the trackpad, and Alt+click.
- Trackpad users: tap-to-click is on by default in ChromeOS, so a
  two-finger tap works out of the box. The README will include the exact
  settings path in case it was turned off.
- ChromeOS settings worth turning on for this user regardless of input
  device: large cursor and cursor highlighting (Settings › Accessibility ›
  Cursor and touchpad).
- Touchscreen Chromebooks also fire `contextmenu` on long-press; the two
  paths are de-duplicated within one second.
- While a name is being read, the control gets a thick highlight outline so
  sight and sound line up. If reading was in progress, it resumes with the
  current verse afterwards.

**Press feedback and forgiveness**

- Activation happens on `click` (pointer down and up on the same control),
  never on pointer down, so a slip does not fire.
- The button inverts for 150 ms on press and the confirmation is spoken.
- Repeated activation of the same control within 400 ms is ignored
  (tremor double-fire). Up/Down list arrows are the exception: holding them
  auto-repeats on purpose.

**Keyboard**

Space: play/pause. Left/Right: previous/next verse. Up/Down (and
PageUp/PageDown): previous/next chapter. B: book list. C: chapter list.
S: settings. Esc: back. Each shortcut speaks the same confirmation as the
button.

**Sizing and contrast**

- All sizes are relative (viewport units, CSS grid), so ChromeOS display
  scaling and browser zoom both enlarge the app cleanly.
- Buttons: bold Atkinson Hyperlegible, label about 40 px at Chromebook
  size, 8 px border, 14 px gaps, a large arrow glyph with a small caption
  where direction matters.
- Focus ring: 8 px, in the theme's highlight color, never removed.
- Current verse: inverted colors, 8 px border, extra padding, kept centered.
- Color schemes are CSS variables. Dark: white on black, yellow on black.
  Light: black on white, black on pale yellow (less glare than pure white).
  No information is carried by color alone.

**Works with ChromeOS assistive tech too**

Real `<button>` elements with accessible names, `aria-current` on the
current book, chapter and verse, a live region for location changes.
ChromeVox and Select-to-speak will therefore work. If someone runs
ChromeVox, they can turn off "Speak button names" so the two voices do not
talk over each other.

**Persistence**

Position (book, chapter, verse) and every setting are saved on each change
and restored at launch.

## 8. Hosting, install, updates

Live since 2026-10-10: repository https://github.com/analyticalchem/bible-reader,
app at https://analyticalchem.github.io/bible-reader/ (a project site in its
own repository; the main analyticalchem.github.io site is untouched and does
not link to it). Commits carry the GitHub username and no email address.


1. Create the GitHub repo; push. A GitHub Actions workflow builds with Vite
   and deploys `dist/` to GitHub Pages. URL:
   `https://<user>.github.io/<repo>/`.
2. On the Chromebook, open that URL in Chrome, then Chrome menu › Cast, save,
   and share › Install page as app (older Chrome: "Install"). Pin the app to
   the shelf so it is one big click away.
3. The service worker precaches the app and all Bible text, so it works
   with no internet after the first load. Updates install silently on the
   next launch; no prompts for the user to read.

## 10. iOS later: what it changes today

Not planned in detail yet. These choices are being made now so the port is
a wrapper, not a rewrite:

- **Reading behind an interface.** The Web Speech API inside an iOS web
  view stops when the screen locks and offers few voices, so iOS would swap
  `TtsReader` for a native text-to-speech plugin, or use pre-generated
  audio, which plays in the background with Capacitor's audio mode.
- **Both activation modes already use pointer events** and a hold timer.
  On iOS in click mode, a long press reads the name; in hold mode, a tap
  reads and a hold activates. CSS sets `-webkit-touch-callout: none` and
  `user-select: none` on controls so the system callout and text selection
  do not interfere.
- **No hover-dependent UI.**
- **Relative asset paths** (`base: './'`) so the same build runs from a
  GitHub Pages subfolder and from inside an app bundle.
- **Safe-area insets** in the layout CSS from the start; the text panel
  moves above the controls in portrait, which the mockup already does.

## 11. Decisions

Confirmed in review on 2026-10-09:

1. KJV, the only bundled translation.
2. Pause stops and remembers; Play restarts the current verse from its
   beginning.
3. Verse numbers are never spoken during continuous reading.
4. Both light and dark color schemes ship (two of each).
5. Mouse and trackpad are both first-class for right-click.
6. Reader layout: no title row; five rows (testament, book with arrows,
   chapter with arrows, play with verse arrows, settings at the bottom);
   names abbreviate instead of wrapping (section 5.1).
7. The testament button switches to the other testament's first chapter.
8. Choosing a book returns to the reader at chapter 1.
9. The verse being read is not highlighted; the panel keeps the line being
   read centered instead (the ring was tried and removed).
10. Buttons can activate by click or by hold, with an adjustable hold time.
    Spoken names are statuses, never instructions.
11. The verse panel is called "Scripture" in settings (Show Scripture,
    Scripture size), and button text has its own size setting.
12. Voices: the Chromebook's own voices first; pre-generated natural audio
    is held in reserve and revisited after the initial build if the voices
    are unsatisfactory.

Made in this plan and not yet questioned:

13. No framework; Vite + TypeScript; GitHub Pages hosting.
14. While paused, Next/Prev Verse reads that single verse and stops.
15. In landscape with Scripture shown, the panel sits beside the controls
    rather than above them, so the buttons stay tall.

Open: nothing at the moment.

## 12. Questions worth asking the person it is for

1. Click mode or hold mode, and how long a hold feels right?
2. Do they want to see the text at all, or is audio-only with huge buttons
   better?
3. Which color scheme do they reach for first?
4. How fast should the voice talk, and is the Chromebook voice acceptable?

## 13. Risks

| Risk | Mitigation |
|---|---|
| ChromeOS voice quality disappoints | Install the voice packs; judge after M2 on real chapters; pre-generated audio held in reserve (4.3) |
| Network-voice 15-second cutoff | Per-verse utterances; split long verses; prefer local voices |
| Pause/resume bugs in Web Speech | Never use resume; restart the verse |
| Hold mode makes everything slow or is forgotten | Default to click; hold time adjustable down to half a second; the mode is announced when changed |
| Adjacent arrow rows confused with each other | Row gap, captions under glyphs, spoken confirmations that name the row ("Next chapter") |
| Buttons too small once Scripture size is large | Scripture panel beside the controls in landscape; Scripture-off mode; lists page by fewer items at larger sizes; test at 1366 × 768 |
| Name pronunciation | `spoken` field for books; substitution map for in-text names |
| Right-click is physically hard on a trackpad | Two-finger tap; Alt+click; hold mode's tap-to-read; external mouse; keyboard |
